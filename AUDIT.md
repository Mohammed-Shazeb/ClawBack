## Findings

### CRITICAL

**C1 — Generated Convex API file had been hand-fabricated and committed.**
`convex/_generated/api.d.ts` at commit `4cfe100` contains the comment
"the module list below was extended by hand because `npx convex dev` could not run
in the environment this milestone was built in." Fabricated codegen is a
correctness hazard: the file is the contract Convex types and the client rely on,
and a hand-written approximation can silently disagree with what the deployment
actually serves. **Fixed**: the file was regenerated by a real
`npx convex dev` run against the local deployment; the hand-edit note is gone and
the module list now matches the deployment.

**C2 — A second statement reset an already-analysed case back to `ANALYZING`.**
`convex/emails.ts` `applyExtraction` patched `status: "ANALYZING"` unconditionally.
Any case that had already reached `RESEARCHING` / `EVIDENCE_FOUND` would be dragged
backwards by a later inbound statement, so the UI would show work in progress while
evidence and assessments already existed. This directly contradicts the "no fake
transitions" and "UI reflects actual backend state" requirements. **Fixed**: the
transition now only applies when the case has not yet moved past analysis.

**C3 — Research re-runs could stack up duplicates instead of being idempotent.**
`researchStoreResults` deletes the previous sources for a deduction only *inside*
the same mutation that stores the new ones, but `claimForResearch` returned a claim
for any deduction whose status was not already `RESEARCHING`. A manual
`retryResearch` racing a scheduled run could therefore have two live passes; the
second pass to store would delete the first pass's sources and write its own,
producing churn and a reset assessment rather than a stable, traceable evidence
chain. **Fixed**: a research pass now carries a token that is checked at store
time, so a superseded pass cannot write.

**C4 — Duplicate `RESEARCH_COMPLETED` timeline events.**
`e2e` showed a case with two statements producing a `RESEARCH_COMPLETED` event per
pass per deduction (8 deductions → many events), and the store mutation inserted a
`RESEARCH_COMPLETED` event on every pass including passes that replaced identical
evidence. Combined with C3 this produced the duplicated timeline visible in the
live database. **Fixed**: store is now guarded by the pass token and writes one
event per real completed pass.

**C5 — Concurrent deductions stranded one another mid-pipeline (found live, not by reading).**
This was the most serious defect and it only appeared once the whole pipeline was
actually run against a deployment. Convex mutations re-run on write conflict and abort
after exhausting their retries. `claimForResearch`, `claimForAssessment`,
`storeResearchResults` and `storeAssessment` each read or wrote rows shared by every
sibling deduction of the same case (the `cases` document, and the `deductions`
collection via `recalcDisputableTotal`). Four deductions therefore contended on every
step. The observed symptoms in the dev log were:

```
[CONVEX M(research:claimForResearch)] Documents read from or written to the "deductions"
table changed while this mutation was being run and on every subsequent retry.
A call to "assessments.js:claimForAssessment" changed the document with ID "..."
```

The failure mode was silent and severe: a deduction would sit at `PENDING` or
`ASSESSING` forever with **no recorded error**, the case total stayed at 0, and the UI
showed a plausible-looking "checking the sources…" state that would never resolve —
exactly the "failed AI processing leaves a misleading successful state" class of bug
the brief requires us to rule out. Worse, the assessment catch block also contended, so
`failAssessment` could not run either and the deduction was never even marked failed.

**Fixed** by making every write single-document where possible and moving all shared-row
writes into their own small, independently retryable transactions:

- `claimForResearch` / `claimForAssessment` now touch only the deduction row; the case
  data they used to read is fetched by the new `getDeductionContext` /
  `getAssessmentContext` queries.
- `storeResearchResults` no longer advances the case. The advance is the separate
  `advanceCaseToEvidenceFound` mutation, which is small, forward-only and idempotent.
- `storeAssessment` / `failAssessment` no longer recompute the case total. That is now
  `refreshCaseDisputableTotal`, a separate mutation.
- `failResearch` no longer reads the case row (the case id is already on the deduction).

Losing the total refresh is now benign rather than fatal: the assessment itself is
already committed, and the next pass recomputes the summary. Verified by re-running the
pipeline: all four deductions reach `COMPLETED`, and the case total settles at 500
(capped painting 300 + carpet 200, with `LIKELY_VALID` and `NEEDS_MORE_INFORMATION`
contributing 0).

### IMPORTANT

**I1 — `validatedAssessmentValidator` widened source ids to a plain string array.**
`convex/assessment.ts` `validateAssessment` returns `assessmentSourceIds: string[]`,
and `convex/assessments.ts` cast it back with `as Id<"sources">[]`. The cast is
sound at runtime (ids come from `claim.sources`) but the widening removes the
compiler's ability to catch a genuinely wrong id. **Fixed**: the validator now
returns `Id<"sources">[]` and the cast is gone.

**I2 — Case `potentiallyDisputableAmount` was not recomputed when research reset.**
`claimForResearch` cleared the per-deduction assessment but did not always leave
the case total consistent for the intermediate state; the `recalcDisputableTotal`
call is present, which is correct, but the surrounding status logic (C2) meant the
case could be marked `ANALYZING` while the stored total still reflected completed
assessments. **Fixed** as part of C2/C3.

**I3 — `retryResearch` / `retryAssessment` / `retryProcessing` are public mutations
guarded only by a `userId` argument.** Authorization is a comparison against the
case owner, which is the established pattern for this milestone's demo identity
(see ACCEPTED below), so this is consistent — but the mutations would be safer if
the exact set of allowed prior states were asserted. `retryResearch` accepts a
deduction in any non-`RESEARCHING` state including `COMPLETED`, which is intended
(re-run), and `retryAssessment` only checks `ASSESSING`. **Not changed**: intended.

**I4 — `storeResearchResults` stored `relevantText` from the provider's
description as a fallback.** When passage extraction found nothing, the code fell
back to `result.description`, which is provider-generated summary text rather than
an authoritative passage. Displaying that as "the relevant passage" overstates what
was retrieved. **Fixed**: the fallback now stores no passage and the UI says so
explicitly.

### ACCEPTABLE

**A1 — Demo single-user identity.** `users.ensureDemo` creates one shared user and
the browser passes that `userId` to every query. Every query re-checks ownership
server-side, so a second user id genuinely cannot read another user's case (verified
in the e2e run). Real authentication is out of scope for this milestone.

**A2 — Attachments are metadata only.** The schema and UI both state that
attachment contents are not read. This is consistent and honestly labelled.

**A3 — Official-source filtering is TLD/host based.** `classifyAuthority` uses a
narrow allow-list (`.gov`, `state.xx.us`, legislative/court hosts). It will miss
some authoritative sources on other domains and is deliberately conservative rather
than permissive. Acceptable for this milestone.

**A4 — No OCR.** Known limitation, documented.

**A5 — The case disputable total can be briefly stale.** Since `refreshCaseDisputableTotal`
runs as its own transaction, a case's summary total can lag the last stored assessment by
one pass. This is deliberate: it is strictly better than the alternative (a contended
write that loses the assessment entirely), the next pass corrects it, and the UI always
shows the per-deduction assessments, which are the authoritative figures.
