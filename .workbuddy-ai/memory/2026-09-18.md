# 2026-09-18 — "Your workspace is still loading" on the New Case page

## The report

Creating a case showed a permanent `Your workspace is still loading. Try again in
a moment.` and the form would not submit.

## Diagnosis (not a code bug)

`components/new-case-form.tsx:57` falls back to that message when `useDemoUser()`
returns a `userId` of `null` and no `error`. The real cause was that **the Convex
backend was not running**:

```
port 3210 — nothing listening        <- the Convex deployment
port 3000 LISTENING                  <- Next.js, so the page still rendered
curl http://127.0.0.1:3210/version -> os error 10061 (connection refused)
```

`NEXT_PUBLIC_CONVEX_URL=http://127.0.0.1:3210`, so every Convex call hung. The
frontend rendered because it is static; nothing that needs the backend could
resolve.

**Why it died:** `npx convex dev` and the mocks had been started as background
tasks in the previous session. Those are tied to the session and do not survive
it. Same trap as rule 20 in MEMORY.md — the stack must be restarted, and the app
gives no hint that this is what happened.

Fix: restarted `npx convex dev` (verified `√ Convex functions ready!`, per rule
16) and `node scripts/mock-providers.mjs`. Then confirmed the exact call the form
makes:

```
users:ensureDemo            -> {"status":"success","value":"k1755gzgavr4da73eeft5bvfr18edjk0"}
cases:createWithInbox       -> {"status":"success","value":"j57bxkk7x0s62nx5zvgpxwg4dh8emcnn"}
```

That created one throwaway case in the local DB (there are already 50+ from e2e
runs). No delete mutation exists.

## The real bug this exposed (fixed)

`components/demo-user.ts` relied on `.catch()` to surface a connection problem.
**That never fires when the deployment is down.** A Convex mutation against an
unreachable deployment is not rejected — the client queues it against a socket
that never connects, so the promise never settles. Result: `userId` stays null
forever, `error` stays null forever, and the UI shows "still loading" with no
timeout and no way to understand or recover.

Fix: an 8s reachability timeout that replaces the indefinite wait with an
actionable message naming the two commands to start. A slow-but-successful
response clears the warning it raced (`setError(null)` on success), and the
effect is cancellation-safe.

Generalisation worth remembering: **`useMutation`/`useQuery` against a dead
Convex deployment do not reject — they hang.** Any UI that gates on a Convex
result needs a timeout if it is to fail diagnosably.

# 2026-09-18 (later) — dev-experience fixes

Both items I had flagged in FINAL-REPORT.md as remaining issues are now done.

## `npm run verify:e2e` streams instead of buffering

It collected every check and printed them only at the end, so a run whose mock
had died sat silent for minutes and looked identical to a hang (a 4m50s run was
invalid for exactly this reason). `check()` now prints immediately and keeps a
count; `waitFor` announces what it is waiting for and repeats after 5s.

Proved by running it and reading the log mid-run: **85 lines present 12 seconds
in**, where before there were 4 (just the npm banner). The `waitFor` announcement
also showed up in that partial log (`... waiting for concurrent regenerations
settle`), confirming both halves work.

Note the log-reprinting in `main().catch` was removed — the checks have already
streamed, so only the abort itself is printed.

## `npm run stack` — one command for the whole local stack

`scripts/dev-stack.mjs`, dependency-free. Starts `npx convex dev`, the mocks and
`next dev`; prefixes and colour-codes each child's output; prints a readiness
line per service (including Convex's own "functions ready", the only proof the
deployment has the current code); skips any service whose port is already
listening; and shuts the rest down if a child exits unexpectedly.

**Fixed a real Windows defect in it:** with `shell: true` the handle held is
`cmd.exe`, not the server, so `child.kill("SIGTERM")` terminates the shell and can
leave `convex dev` / `next dev` running and detached — exactly how these services
get orphaned, and an orphaned backend holds its port while answering nothing.
Shutdown now walks the tree with `taskkill /pid <pid> /T /F` on Windows.

Verified from cold (all six ports down): all three came up, then
`users:ensureDemo` resolved and `GET /cases/new` returned 200.

# 2026-09-18 (later still) — Phase 2 coverage gaps, then the live run found two real bugs

## Phase 2 gaps closed

Three gaps from the brief's reliability list had no coverage anywhere. Two were
already guarded and are now *proved* guarded; one had no guard at all and was
fixed in the mock's contract.

- **Missing case.** `cases:get` returns `null` (not an error) for a case that does
  not exist — deliberately different from the `Unauthorized` thrown for someone
  else's case. Convex ids are checksummed, so a valid-but-nonexistent id cannot be
  fabricated over the HTTP API; the path is only reachable through the UI harness
  fixture. Added a section that renders `CaseOverview` with a real case *and* with
  `{"cases:get": null}`, as a pair — the negative half alone would also pass for a
  page that renders nothing. The positive half asserts the money block's share is
  **derived** from the two stored figures (45% of $1,000 from a $450 disputable
  total), which is the assertion that fails if a total is ever hardcoded.
  Proved by control: hardcoding a mismatched disputable total failed exactly that
  one check. 149 → 167 UI checks.
- **Empty landlord response.** `analyzeLandlordResponse` refuses
  `!claim.body.trim()` before any model call. Proved by control: removing the guard
  made an empty reply come back `COMPLETED` — the model **invented a reading out of
  nothing** — and appended a prompt to the provider log. 13 e2e checks failed.
- **Reading the same reply twice.** `retryResponseAnalysis` refuses a reply whose
  status is `COMPLETED`, and `claimResponseAnalysis` only claims `PENDING`/`FAILED`.
  Covered by a new e2e section along with the empty-reply case.

Also: the UI harness had to move to a CJS bundle, because the real `next/link` is
CJS and dynamically requires `react/jsx-runtime`; only `next/navigation` is stubbed
now. And the stub needed `useAction`.

## The live OpenAI path started working, and immediately found two real defects

`verify:live` had been reporting `LIVE VERIFICATION PENDING` (402, "available only
with a subscription"). Re-run today it served the model — and two checks failed.

**Bug 7 — the structured-output contract silently depended on the provider.**
The model returned the letter as `{"letter": "…", "supportingSourceIds": […]}` for
a schema asking for `recipient`/`subject`/`body`. The letter content was excellent;
only the envelope was wrong, and the whole step was discarded. Probed the gateway
directly: it answers **`200 OK` to a `json_schema` request and ignores the schema
entirely**, so the app's existing HTTP-400 fallback never fired. Fixed by carrying
the schema in the prompt on **every** call, not just in the fallback. Verified by
A/B probe: with the schema only in `response_format` the keys are wrong; with it in
the prompt they are exactly right.

**Bug 8 — the prompt had no rule for a partial settlement.** For "I will refund
$450 for the carpet… I am not going to refund the painting or the cleaning" the
model set `acceptsDispute` *and* `rejectsDispute` to true, and
`validateResponseAnalysis` discarded the reading — correctly. The validator was
right and the prompt was wrong: a partial concession is the ordinary outcome of a
deposit negotiation and the prompt said nothing about it. Fixed by scoping both
flags to the dispute **as a whole** and stating that a mixed reply sets both false
and is recorded via `offersPartialReimbursement`.

After both fixes: **`verify:live` 21/21, 0 skipped** — OpenAI 16/16, Firecrawl 3/3,
AgentMail credential 2/2.

## Process notes worth keeping

- **An orphaned Convex backend serves stale code.** My first e2e run after the
  bug-7 fix failed two new checks; the backend on 3210 was an orphan from a
  previous session that had never received the change. `npx convex dev --once`
  refused ("a local backend is still running on port 3210"). Recovering meant
  stopping the process on 3210 (`netstat -ano` for the PID — the sandbox can't see
  processes otherwise — then `Stop-Process`) and starting a fresh `npx convex dev`.
  The same two checks then passed with no code change.
- **`npm run stack` was still supervising from the previous session.** Killing the
  Convex backend and then `next dev` made it shut the whole stack down, which is
  the script working as designed.
- **`next build` cannot exit cleanly here.** It compiles, typechecks and generates
  all six static routes (real `.next/BUILD_ID`), then dies in *finalization* on
  this environment's bulk-delete guard. Established that this is **inherent**: the
  build's own cleanup deletes 55 files and the guard refuses the 50th, so
  pre-clearing `.next`, running from a fresh turn, and stopping `next dev` all
  make no difference. The guard (`CODEBUDDY_SAFE_DELETE_BULK_GUARD`, enforced by
  an external helper) is a safety control and was left alone. Judge the build by
  its artifacts.

## Convex backend setup — what the code actually requires

Gathered while answering "how to setup convex backend":

- The functions read **exactly nine** env vars, all set on the **deployment** with
  `npx convex env set`, never in `.env.local` (which only Next.js reads):
  `OPENAI_{API_KEY,BASE_URL,MODEL}`, `FIRECRAWL_{API_KEY,BASE_URL}`,
  `AGENTMAIL_{API_KEY,BASE_URL,WEBHOOK_SECRET,DOMAIN}`.
- `AGENTMAIL_WEBHOOK_SECRET` is **required**: `convex/http.ts` fails closed and returns
  `503 webhook_not_configured` without it, so an unset secret silently breaks all inbound
  mail. `AGENTMAIL_DOMAIN` is read at `agentmail.ts:120` but is optional.
- The webhook is `POST /agentmail/webhook` (`PATH` in `convex/http.ts`) and lives on the
  **`.convex.site`** host (HTTP actions), not `.convex.cloud` (functions). Registering the
  `.convex.cloud` URL with AgentMail would 404.
- Current state: `CONVEX_DEPLOYMENT=anonymous:anonymous-ClawBack` — an **anonymous local**
  deployment, state in `.convex/local`, no Convex account linked. `NEXT_PUBLIC_CONVEX_URL`
  is `http://127.0.0.1:3210` (functions) and `NEXT_PUBLIC_CONVEX_SITE_URL` is
  `http://127.0.0.1:3211` (HTTP actions). There is no `convex.json`.
- Going to the cloud needs `npx convex login` (interactive — a browser flow I cannot
  complete on the user's behalf), then `npx convex dev` to create/link a project or
  `npx convex deploy` for production, then re-setting all nine vars with `--prod`, since
  env vars are per-deployment and do not carry over.
